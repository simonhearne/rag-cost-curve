## The question, and the answer

At what query volume does a dedicated retrieval index start being cheaper
than replaying an agent's full history on every query? Two token traces do
the work: agent-memory replay-vs-index (`results/ws6b/`, at 98,134 /
392,116 / 1,221,906 tokens of history, n = 12 / 12 / 38) and code-search
agentic-grep-vs-index (`results/ws6a/`, 6.23M tokens, n = 40, plus scaling
subsets at 259k / 1.14M tokens, n = 10).

Under the Claude regime, live search held to its **measured** cache hit
rate (S 1.000 — the smoke run's cache was already warm — M 0.917, L
0.974) and the index carrying the running cost of the smallest dedicated
instance that can hold it (`r8g.large`, $86.1/month floor):

| size | history tokens | live $/query (cached) | index $/query | index floor $/day | **Q\* Claude** | Q\* OpenAI | Q\* open-weight |
|---|---|---|---|---|---|---|---|
| S | 98,134 | 0.0199 | 0.0115 | 2.828 | **334** | 340 | never repays † |
| M | 392,116 | 0.2030 | 0.0124 | 2.828 | **15** | 11 (long-context tier) | window exceeded |
| L | 1,221,906 | 0.2902 (prompt truncated to 959k) | 0.0188 | 2.828 | **10** | window exceeded (959k > 922k) | window exceeded |

**Answer: yes, the index breaks even at every measured size — 334 / 15 /
10 queries per day against the `r8g.large` floor** — inside the abstract's
"tens to hundreds" at all three points. † At S, the open-weight regime's
cached replay costs ≈$0.00001/query (measured hit rate 1.0, and
prefix-cache hits assumed free), so live search is cheaper per query and
the index never repays; drop the hit rate to a still-generous 0.9 and the
same regime gives 3,257 queries/day.

A far more dramatic number exists in the underlying per-configuration cost
data — that the index "repays its build in 0.07 queries" — and it must not
be substituted for the figure above: it measures a narrower comparison
than the live-search-vs-index break-even this claim makes, so quoting it
in place of 334 / 15 / 10 would overstate the case (`results/ws6b/`).

But that headline is the instance floor's number, not the embedding's, and
the single knob that decides whether it applies at all is a deployment
question, not a price:

- **On a cluster you already run** — the index costs its marginal
  gigabytes, not a dedicated box — break-even falls to **0.005 / 0.001 /
  0.002 queries per day**: one query every six months, three years, and
  sixteen months respectively. The index at these sizes is 2 MB.
- **On the code-search workload, on `fastapi`** (`results/ws6a/`),
  agentic grep is cheaper per query than the index at every measured size
  ($0.036 vs $0.038, $0.036 vs $0.040, $0.054 vs $0.067) — **on that
  repository the index never repays, at any volume.** That is a fact about
  `fastapi`, whose parametric arm — no repository access at all — scores
  **0.625** judge accuracy (`results/ws6a/summary.csv`): the model already
  knows much of what grep would find, so grep's loop is short and cheap.
  On `fastapi` a break-even exists only if "live" is redefined as stuffing
  a 960k-token prefix on every call: 12 queries/day under Claude, and the
  prompt does not fit OpenAI's or the open model's context window. **On a
  repository the model has never seen** (parametric floor 0.000), the same
  arms give a finite break-even at every measured size — 37 / 26 / 64
  queries/day at k=10 — and that curve, with its own caveats, is the
  section "The second curve" below.

That gap — dedicated floor vs marginal capacity on a box you already run —
is **69,000×** in Q\*, the largest swing any knob produces in this whole
model (§ below). **It is the deployment question this talk should close
on: are you buying a box for this, or do you already run one?**

## The second curve — the same question on a repository the model has never seen

`results/ws5/break_even.csv`, rows `workload == "code_unseen"`; token
traces from `results/ws6c/scaling.csv` (WS9, run 2026-09-15). Every branch
letter below is a **lookup** against the pre-registration in
`docs/superpowers/specs/2026-09-15-ws9-unseen-corpus-cost-curve-design.md`
§4, written before any S or M row existed.

The code-search corner above is a single repository, `fastapi`, on which
the model scores 0.625 with no repository access. WS9 puts the same three
arms — agentic grep, the index at its shipped default k=10, and the index
bound to k=3 — on `agentic-hil/agentic-hil` at three nested sizes, the
corpus WS6c's non-memorisation gate cleared at **0.000**. Same 37
questions at every size, so no question enters or leaves the panel as the
corpus grows; same agent, judge, embedding model, package and turn cap.

Under the headline mode (Claude regime, dedicated `r8g.large`,
`pca_uc_384_sq8`), from `results/ws5/break_even.csv`:

| size | corpus `count_tokens` | files (`files_text_allowlisted`; tracked 49 / 212 / 382) | grep $/query | index $/query, k=10 | k=3 | saving/query, k=10 / k=3 | floor $/day | **Q\* k=10** | **Q\* k=3** |
|---|---|---|---|---|---|---|---|---|---|
| S | 1,139,248 | 49 | 0.1442 | 0.0677 | 0.0926 | 0.0764 / 0.0516 | 2.828 | **36.99** | 54.81 |
| M | 2,017,476 | 172 | 0.1897 | 0.0799 | 0.0705 | 0.1099 / 0.1193 | 2.828 | **25.73** | 23.71 |
| L | 4,307,363 | 342 | 0.1392 | 0.0949 | 0.1050 | 0.0443 / 0.0343 | 2.828 | **63.79** | 82.52 |

n = 37 per cell; $/query is the mean agent-billed cost, judge excluded
(`results/ws6c/scaling.csv`, `cost_agent_billed`). Break-even is the
floor divided by the mean per-query saving: **a ratio of means, which
needs no separating interval to be stated.** What it does not license is
the word "wins" — see the U-series below.

**Branch F — F1.** Break-even is **finite at every measured size**. Grep
is the more expensive arm per query at S, M and L, on both index arms, so
the "never repays" verdict from `fastapi` does not carry to a repository
the model has not seen. **Branch B — B1.** All six Q\* values lie inside
the abstract's [10, 1000): the lowest is 23.7 (M, k=3) and the highest
82.5 (L, k=3). That is "tens", never "hundreds": on this corpus the
point-estimate break-even against a dedicated instance is a few dozen
queries a day.

**The curve is not monotone, and the report does not know why.** Q\* runs
37 → 26 → 64: the largest corpus has the *worst* break-even of the three.
The spec's H1 — the saving widens with size and Q\* falls — did **not**
hold. The saving is set by the grep arm's cost, which is non-monotone
(0.144 → 0.190 → 0.139), while the index arm rises steadily with size
(0.068 → 0.080 → 0.095). Whether the bump at M is a property of the corpus
or of 37 questions cannot be told from this data: every primary paired
cell resolved U3 (below), and the per-arm size-span deltas
(`results/ws6c/paired_ci_unseen_scaling.csv`, `contrast_kind ==
"size_span"`, exploratory, not pre-registered) put the grep arm's L−S
prompt-token change at a median +35 with CI [−1,927, +5,655]. The point
estimates are the curve; **the curve's shape is not established.**

**Branch K — K2: the k=10 / k=3 order does not survive the curve.** The
deck quotes the L pair "58.94 at k=10, 70.44 at k=3" (n = 40; see the n
note below) and the k=10-is-cheaper order holds at S (36.99 < 54.81) and
at L (63.79 < 82.52), but **reverses at M** (25.73 > 23.71), where the
bound arm is cheaper per query than the default (0.0705 vs 0.0799). The
k=3 arm's cost relative to k=10 goes +37% / −12% / +11% across S / M / L.
The paired cell behind the reversal, `indexed_topk3 − indexed` at M, is
U3 (median −4,575 prompt tokens, CI [−10,476, +407]), so the reversal is a
point-estimate ordering, not a separated one — and so is the order at S
and L. The talk may not say the shipped default is the cheaper index
setting; on this corpus it is at two sizes of three and the pair is not
separated at any.

**Branch U — U3 in eight of nine cells, as pre-declared.** Nine paired
median deltas over `prompt_tokens` (3 contrasts × 3 sizes), n = 37,
10,000-resample percentile bootstrap, seed 42, α = 0.05, **no multiplicity
correction** — ~0.45 cells resolve by chance under a global null
(`results/ws6c/paired_ci_unseen_scaling.csv`; the table is in
`results/code-retrieval.md`, WS6c "The size sweep"). Every `indexed −
agentic` cell is U3: S −1,743 [−13,337, +3,075]; M −3,467 [−21,743, +846];
L −3,228 [−12,884, +961]. Every `indexed_topk3 − indexed` cell is U3. The
one cell that resolved, `indexed_topk3 − agentic` at M (median −8,263, CI
[−23,324, −2,576], `sign_p` 0.0026, **U1**), is a single isolated
resolution among nine unadjusted cells, flanked by U3 for the same contrast
at S and L; spec §4.1 and the bootstrap script's own printed disclosure say
such a cell **may not be reported as a finding**, and it is not. Spec §4.1
declared U3 at every size the expected outcome before the data existed —
WS6c's own L cell at n = 40 missed excluding zero by 85 tokens — so U3 here
reads as predicted, not as a failure found late. **Corollary, binding: the
report states the curve and its point estimates; it may not say the index
wins at any size, because the primary contrast resolved U3 at every
size.**

**H2 did not fire.** The spec's H2 was that at S — a 49-file tree — grep
might be *cheaper* than the index, making Q\* infinite there. It is not:
0.0677 vs 0.1442 per query. Stated as the finding about scale it is:
between 1.1M and 4.3M tokens on an uncontaminated corpus there is no
measured size at which grep is the cheap arm. Stated as what it is not:
this says nothing about whether scale explains `fastapi`; that question is
the C-series, next.

**The C-series — C1 on every matched pair; the contamination explanation
survives, unproven.** (`results/ws6c/matched_size_contamination.csv`.)
Two scopes are *matched* iff their measured `count_tokens` lie within
2.0× — the rule fixed in spec §3.2 before S and M were measured. Three of
nine pairs land in band, the three the spec predicted:

| pair | `count_tokens` ratio | files, `fastapi` / unseen | `fastapi` cheaper arm ($/query) | unseen cheaper arm ($/query) | branch |
|---|---|---|---|---|---|
| `fastapi` M vs `agentic-hil` S | 1.001 | 1,112 / 49 (22.7×) | agentic (0.0355 vs 0.0400) | indexed (0.0677 vs 0.1442) | **C1** |
| `fastapi` L vs `agentic-hil` L | 1.447 | 2,888 / 342 (8.4×) | agentic (0.0543 vs 0.0666) | indexed (0.0949 vs 0.1392) | **C1** |
| `fastapi` M vs `agentic-hil` M | 1.772 | 1,112 / 172 (6.5×) | agentic (0.0355 vs 0.0400) | indexed (0.0799 vs 0.1897) | **C1** |

Overall **C1**: at matched corpus size the per-query winner differs across
the two corpora, so size alone does not explain the `fastapi` result and
contamination remains the *candidate* explanation — candidate, because
this test can rule size out, not rule contamination in. Three things
about this comparison, stated so nobody has to discover them:

- **It is unpaired and carries no interval.** Different questions,
  different n (`fastapi` 10 at S and M, 40 at L; 37 here), no row
  correspondence; the CSV's `pairing` column says so on every row. It is
  a described comparison of point estimates, exactly as WS6c's sign
  reversal is.
- **The file counts are badly mismatched, and the mismatch cuts against
  C1.** Grep's cost scales with how much tree it must search, so the
  small-file-count side of every pair — always the unseen corpus —
  favours the agentic arm, the arm C1 needs to lose there. C1 was
  obtained against that confound. The `file_ratio` column is
  **directional only**: it divides WS6a's `files` (`results/ws6a/repo_stats.csv`)
  by `files_text_allowlisted` here (`results/ws6c/scaling_corpus_stats.csv`,
  where the tracked counts are 49 / 212 / 382), and the two are not
  established to be the same measure.
- The C-series is defined over `agentic` vs `indexed` only — `fastapi`
  has no `indexed_topk3` arm at S or M — and says nothing about top-k
  across corpora.

**The caveats that already exist at L apply to any curve drawn through
it**, carried forward from `results/code-retrieval.md` unchanged:

- the paired median interval for `indexed` vs `agentic` prompt tokens
  **straddles zero** (`sign_p` 0.081, `results/ws6c/branches.csv`, branch
  P3);
- the agentic arm **hit the turn cap on 2 of 40 runs**, so the saving is
  the **conservative end**;
- the per-arm medians in `results/ws6c/summary.csv` carry the **opposite
  sign** to the paired deltas on this same data — marginal medians are not
  tested comparisons. (This holds for the two `indexed_topk3` contrasts:
  the marginal medians put `indexed_topk3` **above** `agentic` by +4,615.5
  and above `indexed` by +7,899 while the paired deltas are −4,717 and
  −3,961.5; for `indexed − agentic` the two agree in sign, −3,283.5 marginal
  against −5,217 paired.)

The first two recur on the panel: at n = 37 the L cell is U3 with
`sign_p` 0.188, and the grep arm hit the turn cap on 1 / 2 / 2 of 37 runs
at S / M / L (`results/ws6c/scaling.csv`, `hit_turn_cap`), so at every
size the grep arm's cost — and with it the saving and Q\* — is the
conservative end.

**The index footprint is derived, not estimated.** Each size's footprint
is the measured chunk count — **2,099 / 3,324 / 7,441**, `count(*)`
against Milvus in `results/ws6c/index_cost.csv` — × 1536 dimensions × 4
bytes, ÷ the 8.66× `pca_uc_384_sq8` multiplier, through
`cost_model.index_footprint_bytes`: **0.001387 / 0.002196 / 0.004917 GiB**
(1.5 / 2.4 / 5.3 MB), exactly the derivation the `fastapi` rows already
use (`tests/test_ws9_cost_model.py`,
`test_index_footprint_is_derived_from_the_measured_chunk_count`). This
retires the deck's current refusal of the marginal and serverless rows for
this corpus — "agentic-hil's was never measured; estimating it would put
the only estimated number on a chart where everything else is measured or
exactly derived" (`data/SOURCES.md`, `ws5/break_even_ws6c.csv`). Nothing
here is estimated. The marginal rows now exist: at $5.38/GiB-month the
fixed cost is **$0.00038 / $0.00061 / $0.00136 a day** and break-even is
**0.005 / 0.006 / 0.031 queries a day** at k=10 (0.007 / 0.005 / 0.040 at
k=3) — one query every 200, 179 and 33 days. Under the conservative `sq8`
footprint (3.54×): 0.0034 / 0.0054 / 0.0120 GiB and 0.011 / 0.013 / 0.070
a day. The infra-mode knob spreads Q\* by **7,421×** on this workload
(`results/ws5/sensitivity.csv`, `workload == "code_unseen"`), against
69,000× on agent memory; it is the dominant knob here too. The
multipliers carry WS5's standing caveat: measured at 10M × 1024d and
applied as ratios to 1536d vectors.

**n = 37 on the panel; the published WS6c headline is n = 40.** The deck's
L figures, **58.94** (k=10) and **70.44** (k=3), are the same arithmetic
over all 40 `agentic-hil` questions in `results/ws6c/summary.csv`. The WS9
rows give **63.79** and **82.52** at L. The difference is **composition
alone**: three questions (`q09`, `q30`, `q31`) whose gold files lie in
`examples/`, `tools/` and `tests/` are outside S and are excluded at every
size so that one panel runs across the curve; the L runs themselves are
WS6c's frozen rows, not re-run. Per-arm mean $/query at n = 40 → 37:
agentic 0.1387 → 0.1392, indexed 0.0907 → 0.0949, `indexed_topk3` 0.0985 →
0.1050 (judge accuracy 0.900 / 0.975 / 0.950 → 0.919 / 0.973 / 0.946).
Neither pair is more correct; they answer over different panels, and a
reader who meets 63.79 next to 58.94 should find it announced here first.

**The curve spans 3.78×, and the fixed cost is flat across it.** Measured
`count_tokens` 1,139,248 → 2,017,476 → 4,307,363 (1.77× then 2.14×; the
spec pre-registered 3.74× from tiktoken predictions, and the measured span
is 3.78×). Under the dedicated headline `fixed_daily` is **$2.827721 /
$2.827754 / $2.827832** — the $86.07/month instance ÷ 30.4375 plus one-time
embed cost ($0.0148 / $0.0270 / $0.0554, `embed_once`) amortised over 365
days, which is $0.00004 to $0.00015 a day. (Those `embed_once` figures are
not the $0.014457 / $0.022858 / $0.050975 in the Appendix inputs table
(`results/ws6c/index_cost.csv`): the model prices
the **whole-corpus** tiktoken count, 741,343 / 1,352,243 / 2,770,789 ×
$0.02/MTok, while `index_cost.csv` records what was paid on the files
claude-context actually indexed, 722,831 / 1,142,900 / 2,548,757 tokens. The
gap is 2.6% / 18.3% / 8.7% — M's is largest because its non-indexable
tokens, 209k, are nearly L's 222k on a `tiktoken_cl100k` base 49% the
size (`results/ws6c/scaling_corpus_stats.csv`) — and it is invisible in Q\*, since it is
amortised over 365 days. It is the same convention WS5
already uses for the `fastapi` rows.) A 16 GiB instance holds a 5 MB index as easily
as a 1.5 MB one, **so the shape of this curve is set entirely by the
per-query saving; the footprint is load-bearing only in marginal mode**
(`test_the_dedicated_fixed_cost_is_flat_across_the_curve`). Two limits of
the span itself: it is 3.78× where WS6a had 24× and WS6b 12.5×, and the
sweep spans a week of wall-clock as well — the L rows were measured
2026-09-08 (WS6c Phase 3) and the S and M rows 2026-09-15
(`started_at` in `results/ws6c/scaling.csv`). Nothing pre-registered that
gap; the same pinned model, package, prompt and corpus were used, and it
is reported rather than explained away.

**Other regimes, for completeness** (`results/ws5/break_even.csv`, same

(36.84 / 25.70 / 64.12 at k=10); the self-hosted open-weight regime, at
$0.21/MTok blended, puts the same points at 350 / 241 / 582 — the cheaper
the live tokens, the more queries the floor needs.

**Spend.** 222 runs (37 × 3 arms × 2 new sizes), **$26.44** billed of the

## Why the obvious reading is wrong

**"Tens to hundreds of queries a day" sounds like the index almost always
wins quickly. It doesn't — it wins at the price of a small instance
divided by the per-query saving, and that price is a choice, not a law of
the workload.**

**1. The cache hit rate feeding the live side is steelmanned, not
stacked against it.** The live-search baseline uses each size's
*measured* cache hit rate (0.917–1.000), not list price and not a
pessimistic cold-start number. Pushing the hit rate higher — a further
steelman — only *raises* Q\*: at h = 0.5 / 0.9 / 0.95 / 0.99, Claude's Q\*
is S 16 / 69 / 117 / 260; M 3.9 / 15 / 23 / 39; L 1.6 / 5.9 / 8.9 / 15. The
live side at list price (the strawman) gives 15 / 3.7 / 1.5. Steelmanning
the cache is what puts the headline in "hundreds" rather than "single
digits," and the index still wins — this is the standing rule of the repo
applied to its own headline number, not asserted about it.

**2. The 69,000× knob dominates every other lever, by four orders of
magnitude.** Sweeping one knob at a time from the S/M/L base case
(`results/ws5/sensitivity.csv`), and reading direction as: pushing Q\* above 1000,
flipping the per-query winner, or making the live point infeasible
*weakens* C9; pushing Q\* below 10 *strengthens* it ("tens" becomes
"single digits"):

| knob | settings | Q\* at S / M / L | max spread | effect |
|---|---|---|---|---|
| **infra mode** | dedicated floor → marginal GiB | 334/15/10 → 0.005/0.001/0.002 | **69,000×** | strengthens (downward) — the dominant knob |
| live arm uncached | list price | 15 / 3.7 / 1.5 | 21.9× | strengthens; the strawman |
| infra $/GiB-month | ×0.5 / ×2 | 167/7.4/5.2 — 668/30/21 | 4.0× | moves the number; M and L slip to single digits at ×0.5 |
| Claude price | ×0.5 / ×1.5 | 668/30/21 — 223/9.9/6.9 | 3.0× | moves the number; M and L slip to single digits at ×1.5 |
| cache hit rate | miss ÷2 / miss ×2 | 334/22/13 — 334/9.0/7.7 | 2.45× | moves the number; S is pinned at h = 1.0 |
| **regime** | OpenAI / open-weight | 340/11/— ; ∞/—/— | 1.38× where feasible | **weakens**: OpenAI cannot run the L point (922K max input); the open model cannot run M or L (128K) and makes S never repay |
| cache TTL | 1h write (as run) → 5m write | 334/20/12 | 1.35× | moves the number, not the verdict |
| footprint (index compression choice) | pca_uc_384_sq8 8.66× → sq8 3.54× → refine 3.11× | unchanged | 1.00× | **nothing** — a 2 MB index does not fill a 16 GiB instance either way |
| open-weight $/MTok | ×0.5 / ×2 | ∞/—/— | — | nothing at S (cache hits are free regardless) |

Only *regime* moves the verdict against the index, and only by capability,
not price: two of three providers cannot fit the larger live prompts at
all. Under every regime that can run a point, the index wins per query.
Infra price, model price, cache hit rate and cache TTL each move the
*number* within about 4×, keeping Q\* somewhere between roughly 6 and
750/day — inside "single digits to hundreds" either way. The index
compression choice (`results/ws2/`, `results/ws3/`) moves nothing: at
these corpus sizes the index is megabytes, so the compression ratio
chosen doesn't change whether it fits an instance. **Whether the index has
a running-cost floor at all dwarfs all of that — it is a deployment
question, not a price knob, and the talk should say so.**

**3. Below the break-even, the honest advice is simple: don't build the
index.** At S, a dedicated index needs ≥334 queries/day before it pays; a
team asking 20 questions a day of a 98k-token history should replay it,
not index it — the same conclusion the code-search corner above reaches
at every volume, not just below a threshold. High churn does not change
that in the index's favour either: it is cheap to re-embed, and what
churn actually damages is the live side's cache
(`results/ws5/churn.csv`). ⚠️ **This corner is arithmetic, not measured**:
`churn_frac_per_day` is an assumption sweep over churn rates nobody
observed here, evaluated through the cost model. Only the two re-embed
factors below are measured; every churn rate they are multiplied by is
an assumption.
Re-embedding costs churn × corpus embed tokens × a factor
(1 for appends, 5 for a measured mid-file edit) × $0.02/MTok. With an
instance floor in place, re-embedding never dominates it — the two are
equal only at 50–635× the corpus re-embedded per day. Without a floor,
re-embedding passes the (now marginal) fixed cost above **0.9% of the
corpus per day** for mid-file edits or **4.5%** for appends — and even at
100%/day, Q\* stays below one query per day (0.1–0.6). An embedding-model
migration costs the original build again ($0.0126 at L).

The larger churn effect runs the other way: an edit inside the cached
prefix invalidates the cache, so at L, losing the replay cache takes live
search from $0.29 to **$3.84** per query and Q\* from 12 to **0.83/day** —
a 13.2× penalty on the live side. **Churn hurts cached replay more than it
hurts the index.** A third corner — whether the question is already in the
model's training data — is measured, not modelled: the code-search parametric arm (no repository
access, `results/ws6a/`) scored 0.625 judge accuracy on `fastapi` at
$0.009/query, but 0.000 on the agent-memory synthetic corpus
(`results/ws6b/`). That is the cited worked example, not a new benchmark.

**4. The shape, not the crossing point, is the more defensible claim
(C2).** Per query, live search costs the *history* (replay: 98k → 959k
prompt tokens, $0.020 → $0.290 cached) while the index costs the *answer*
(4.6k → 6.4k prompt tokens, $0.011 → $0.019). Before any query is asked,
live search costs nothing and the index costs a floor. Break-even is that
floor divided by the per-query gap, and the gap widens with corpus size
while the floor stays flat — a modelled line only between the two
measured endpoints, nothing extrapolated past them. That the two curves
have different *shapes* survives every knob in the sensitivity table
above; the exact crossing point does not, because it is set by whichever
floor you choose to price.

## What was measured

**The pre-declared test (`results/ws5/break_even.csv`).** The notebook's markdown cell
states the test before the computing cell runs it: Claude regime, measured
hit rate, dedicated `r8g.large`, `pca_uc_384_sq8` footprint — is
10 ≤ Q\* < 1000 at S, M and L? All three sizes pass (table above).
Reported alongside it, as pre-declared rather than added after the fact:
the no-floor case, the code-search case, the crossover-bracket check (the
index is cheaper per query at every measured memory size in
`results/ws6b/`, so the per-query crossover lies below 98k tokens and is
not fitted), and the cache steelman sweep. The same test over the
`code_unseen` rows added 2026-09-15 — same regime, hit-rate basis, instance
and footprint, `live_arm == "agentic"` — passes at all three sizes on both
index arms (branches F1 and B1; the values and every caveat are in "The
second curve" above).

**The correctness gate — passed, with one diagnostic miss reported**
(`results/ws5/postdiction_gate.csv`, 72 rows: 42 from the 2026-09-07 run
and 30 `code_unseen` rows added 2026-09-15 — 3 sizes × 3 arms × 3 bases,
plus the parametric arm at L only). The model was fed each configuration's
*parameters* — prefix as corpus tokens × measured fit fraction, measured
mean uncached and output tokens per query, measured hit rate — and had to
reproduce that configuration's measured mean billed and mean
uncached-list $/query within ±10%:

| basis | rows | worst \|error\| | result |
|---|---|---|---|
| mean billed | 24 (14 + 10 `code_unseen`) | **0.09%** (the `code_unseen` rows: 0.0000%) | pass |
| mean uncached list | 24 (14 + 10 `code_unseen`) | **0.09%** (the `code_unseen` rows: 0.0000%) | pass |
| median, steady-state hit (diagnostic, not asserted) | 24 (14 + 10 `code_unseen`) | 11.3% (the `code_unseen` rows: 8.5%) | 23 of 24 within 10% |

On the two code workloads the model's inputs are the measured per-arm
token means themselves, so a 0.0000% error there is a check that the
wiring reproduces the bill, not a test of a fitted model; the diagnostic
median basis, where the two can differ, is within 10% on all ten
`code_unseen` rows. The gate passed on both bases it was asserted against.
It did **not** pass cleanly on every row it was run against: the one
diagnostic miss is `code / S / indexed` (n = 10, −11.3%), because the
median of per-row sums
is not the sum of per-column medians, and on that cell output tokens
dominate the bill. The tolerance was not widened to hide it — the median
rows stay in the CSV so the effect is visible, and the model predicts
*expected* cost, which is exactly what the mean rows (the ones asserted)
reproduce to a tenth of a percent. What the gate proves: corpus size × fit
fraction plus a hit rate reproduces the bill, so interpolating between
measured sizes in corpus tokens is legitimate — it does not license
drawing conclusions about corpora outside the measured range, and none are
drawn there.

**Pricing regimes.** Three model regimes (Claude, OpenAI, open-weight
self-hosted) and the serving-memory instance rate all went in as fetched
prices, none guessed — including two facts that shape the sensitivity
table above: OpenAI's long-context tier re-prices the *whole* request past
272K input tokens (a fact about that regime's price list, not a finding
about the model), and the open-weight $/MTok figure is derived from a
benchmarked throughput, not quoted from a price sheet. Every value, its
exact source URL, and its fetch date are in the appendix below and
`results/ws5/pricing.csv`.

## Limits and caveats — what a hostile reader checks first

1. **Single workloads.** One synthetic agent history (n = 12/12/38) and
   one repository (n = 40; scaling subsets n = 10). No confidence
   intervals across corpora. The dashed model lines run only between
   measured sizes and stop there.
2. **Tokens were counted by Claude's tokenizer** and re-priced under the
   other regimes. tiktoken measured 26% below Claude's count on the
   repository (`results/ws6a/`), so the non-Claude regimes are
   overstated on input tokens by up to ~1.3x — in the direction that
   flatters the index under those regimes, not against it.
3. **The open-weight $/MTok figure is a derivation, not a bill**: one
   benchmark, one rental price, blended input/output at 100%
   utilisation, prefix-cache hits assumed free, no operations labour
   included. Prefill is faster than decode, so input-heavy live prompts
   are overcharged in this model. Only the S point (98k) and the agentic
   code points fit a 128K window; a genuinely 1M-context open model would
   need its own benchmark.
4. **The instance floor is the load-bearing assumption in the whole
   model, and it is a deployment choice, not a measurement.** Managed
   serverless pricing sits somewhere between "dedicated instance" and
   "marginal capacity" and was not modelled at all.
5. **Laptop latency is excluded.** Nothing in this cost model prices
   time. The underlying index runs were single-node Docker
   (`results/ws2/`, `results/ws3/`, `results/ws6b/`); the code-search
   index (`results/ws6a/`) ran on Zilliz Cloud serverless.
6. **Footprint multipliers were measured at 10M vectors × 1024 dimensions
   (`mxbai`)** and applied here as ratios to 1536-dimension
   `text-embedding-3-small` vectors — a transfer, not a re-measurement.
7. **The measured hit rate at S is 1.0 because the smoke run warmed the
   cache**; the honest cold-start value would be 11/12 = 0.917, which
   would put Q\* at S around 103 instead of 334. The cache steelman
   sweep above covers this range.
8. **Cache TTL**: the underlying token-cost runs (`results/ws6a/`,
   `results/ws6b/`) used 1-hour cache writes (2× surcharge). The
   5-minute write rate (1.25×) is carried in the sensitivity table, not
   as the headline.
9. **Prices are as of 2026-09-07.** `results/ws5/pricing.csv` carries
   every source URL and fetch date, including the quoted "permanent"
   language from the Claude pricing page — this cost model does not
   update itself as prices change.
10. **The priced configuration was chosen using a threshold that has
    since been retired.** `pca_uc_384_sq8` — the index footprint priced
    throughout the break-even, sensitivity and churn tables above — was
    selected because it met a retrieval-quality floor (measured in
    `results/ws4/summary.csv`) that has since been retired as not a
    locatable quantity on this task (`results/recall-vs-quality.md`).
    That retirement is a dependency of *which operating point* is priced
    here, not of the token-cost or footprint measurements themselves.
    Whether pricing a different configuration, chosen under whatever
    standard replaces that floor, would move the break-even numbers
    above is not settled by anything consulted for this document.
11. **The unseen-corpus curve spans 3.78×**, from 1,139,248 to
    4,307,363 `count_tokens`, where the memory curve spans 12.5× and the
    `fastapi` scaling subsets 24×. Three points across 3.78× cannot
    establish a shape: the curve is non-monotone (37 / 26 / 64) and the
    report says it does not know whether that is the corpus or the
    panel. The dashed model lines run only between the measured sizes.
    The S and M rows were measured a week after the L rows they are
    drawn against (2026-09-15 vs 2026-09-08).
12. **One panel of n = 37, and it is not the published n = 40.** Every
    `code_unseen` cell is the same 37 questions; the published WS6c L
    figures (58.94 / 70.44) are over 40. Every primary paired cell
    resolved U3, as spec §4.1 said it would, so the curve is stated as
    point estimates and no size carries a "the index wins" claim. n = 37
    is also below the n at which WS6c's own L cell missed separating by
    85 tokens; adding sizes did not add power at any one size.
13. **One uncontaminated corpus.** `agentic-hil/agentic-hil` is the only
    repository measured with a 0.000 parametric floor, chosen from three
    gate-cleared candidates by a stars-and-creation-date prior, not by a
    measurement (`results/code-retrieval.md`). The C-series is three
    matched pairs against one contaminated repository, unpaired and
    without an interval; it rules size out as the sole explanation of
    the `fastapi` result and rules nothing in.
